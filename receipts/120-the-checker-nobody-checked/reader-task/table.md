## Does the task discriminate?

No. All 50 runs scored 7/7, so the grader never separated a cell or a prompt. Only 3 runs skipped executing code (o55-med-B-5, s55-med-A-3, s55-med-A-5). They still passed both half-up cases (grader cases 3 and 5: 3/3 and 3/3). Every final pricing.py fixes both seeded bugs, `>` versus `>=` and banker's `round()`. The rule comment states both, so reading it is enough. In this task, running code is not what finds the rounding bug. Prompt B did not move the ran-code rate in any consistent direction: Sonnet medium went from 3/5 to 5/5, Opus medium from 5/5 to 4/5, and the other cells were 5/5 under both prompts. B cost more and took longer in every cell, and k never changed. As a reader task, this can show that models verify, but it cannot show that verification changes outcomes. To make it discriminate, the half-up requirement probably has to come from somewhere other than a comment the model reads (untested).
